# 설계 16: 1년치 데이터 성능 점검

학급 25명이 1년 동안 쓰면 관찰 기록 2,000~4,000건, 첨부 1,000~2,000개(사진·음성 수 GB), 단원 16개·차시 400개, 습관 체크 수천 건이 쌓인다. 지금 테스트는 몇 건짜리 데이터로만 돈다. 1년치 데이터에서 느려지는 곳을 찾아 고친다.

## 1. 1년치 데이터 만들기

- Rust 테스트 도우미 `db::testing::seed_year(conn, media_dir, opts)`: 학급 1, 학생 25, 관찰 3,000건(학생 1~4명, 메모 20~120자, 태그 1~3, 성취기준 0~2, 주제책 16권에 고르게, 날짜는 3월~이듬해 2월 학교 날), 첨부 1,500개(사진은 작은 PNG, 음성은 작은 WAV — 크기보다 개수가 중요, 자막 상태 done 70%), 단원 16·차시 400(일부 꼬리 잇기, 활동 카드 연결), 습관 4개 × 25명 × 180일 체크, 평어 초안 일부, 학부모 리포트 일부. 무작위는 시드 고정. 이름·문장은 `data/synthetic/phrases.json`과 가짜 이름 목록.
- 디버그 빌드 전용 명령 `dev_seed_year`(E2E·수동 점검용, 릴리스에서는 등록하지 않거나 항상 거부).

## 2. 시간 측정 (Rust 테스트, `#[ignore]` + 별도 실행)

`src-tauri/tests/perf.rs`: 1년치 데이터를 임시 폴더 DB에 만든 뒤 다음 명령의 핵심 함수 시간을 잰다(각 5회, 중간값). 기준은 **보통 PC에서 체감 지연 없음**을 목표로 한 상한이며, CI 러너에서 넘으면 실패:

| 대상 | 상한(중간값) |
|---|---|
| `observation_list`(최근 20, 거르기 없음) | 50ms |
| `observation_list` 검색어 2낱말 + 기간 | 150ms |
| `observation_count` 같은 조건 | 150ms |
| `portfolio_student` | 100ms |
| `portfolio_class` | 200ms |
| `unit_get`(차시 40개 단원) | 50ms |
| `habit_week`, `habit_student_summary` | 50ms |
| `report_draft` | 150ms |
| `evidence_bundle`(평어 근거 묶음) | 150ms |
| `activity_recommend` | 50ms |
| 백업 만들기(첨부 1,500개, 작은 파일) | 측정만 기록(상한 없음), 진행률 이벤트 간격 확인 |
| 앱 시작 시 마이그레이션 확인 + 자막 대기 정리 | 100ms |

- 결과를 표로 출력(`--nocapture`). 워크플로 `engines.yml`처럼 수동·주 1회 실행하는 `perf.yml`(리눅스 러너로 충분 — DB 쿼리 성능이 대상) 또는 기존 `ci.yml`과 분리.

## 3. 고치기

- 상한을 넘는 곳은 `EXPLAIN QUERY PLAN`으로 원인을 찾아 인덱스 추가(새 마이그레이션 — 기존 항목 수정 금지), N+1 쿼리 묶기, 필요한 칼럼만 읽기로 고친다. 고친 이유를 커밋 메시지와 코드 주석에 남긴다.
- 프런트엔드: 학급 현황 표·타임라인·기록 찾기 결과가 길어질 때 렌더링이 느리면 「더 보기」 단위를 줄이거나(이미 있음) 목록 가상화 대신 단순 페이지 나눔으로 해결(새 의존성 없이).
- 첨부 많은 백업: 진행률 이벤트가 너무 잦아 화면이 버벅이면 간격 조절(100ms 이상).

## 테스트 기준

- `seed_year`가 시드마다 같은 결과, 개수 정확, 모든 외래 키 유효(`PRAGMA foreign_key_check` 빈 결과).
- 위 측정 테스트가 상한 안. 새 인덱스 마이그레이션이 있으면 기존 백업 복원 테스트처럼 이전 버전 DB에서 올라감.

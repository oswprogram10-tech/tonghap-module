# 설계 15: 문의 대응 — 오류 기록과 진단 파일

선생님 PC에서 문제가 생기면 개발자는 그 PC를 볼 수 없다. 앱이 **아이 정보 없이** 무슨 일이 있었는지 남기고, 선생님이 버튼 하나로 문의용 파일을 만들게 한다. 인터넷으로 보내지 않는다(파일을 만들어 선생님이 직접 전달).

## 1. 오류 기록(로그)

- 위치: `<데이터 폴더의 부모>/logs/app.log` (설계 12의 `paths::local_data_dir` 기준). 5MB가 넘으면 `app.1.log`로 돌리고 최대 3개 유지.
- Rust: 가벼운 자체 로거(새 의존성 없이 `std::fs` + `Mutex`) 또는 `log` 파사드 + 파일 출력. 한 줄 형식: `2027-03-05T10:20:00+09:00 ERROR [backup] 메시지`.
- 무엇을 남기나: 앱 시작·종료(버전, 윈도우 버전), 명령 오류(명령 이름 + 오류 문구), 패닉(panic hook으로 위치와 메시지), 엔진 실행 실패(종료 코드 + stderr 끝 400자), 마이그레이션 적용, 백업·복원 시작·결과.
- **남기지 않는 것**: 학생 이름, 메모·자막 내용, 파일 경로 중 사용자 이름 부분(경로는 `%LOCALAPPDATA%\…`처럼 바꿔 적음), 백업 암호. 명령 인자는 기록하지 않는다(오류 문구만). 오류 문구에 학생 이름이 섞일 수 있는 경로가 없는지 테스트로 확인(학급 명단의 이름을 넣은 오류를 만들어 로그에 이름이 없는지).
- 프런트엔드 오류: `window.onerror`, `unhandledrejection`을 Rust 명령 `log_frontend_error({ message, source, line })`로 보내 같은 파일에 기록(메시지는 300자로 자름).

## 2. 화면 오류 경계

- React 오류 경계를 탭 화면마다 씌운다. 렌더링 오류가 나면 흰 화면 대신 "이 화면에 문제가 생겼습니다. 기록은 안전합니다." + 「다시 시도」(그 화면만 다시 그림) + 「문의용 진단 파일 만들기」.
- 칠판 창에도 같은 경계.

## 3. 문의용 진단 파일

- 「정보」 화면에 「문의용 진단 파일 만들기」 → 저장 대화상자(`src/lib/dialogs.ts`의 `saveFile`, 기본 이름 `바슬즐-진단-YYYYMMDD-HHMM.zip`).
- zip 안(새 의존성: 이미 있는 `tar`를 써서 `.tar`로 할 수도 있으나 선생님이 열기 쉬운 zip을 원하면 `zip` 크레이트 — 하나를 고르고 라이선스 파일 재생성):
  - `about.json`: 앱 버전, 교육과정 데이터 버전, 윈도우 버전, CPU·메모리, Vulkan 여부, 엔진 존재 여부, 모델 파일 이름·크기·확인 여부, DB 스키마 버전, 개수(학급·학생·관찰·첨부·단원·습관) — 숫자만.
  - `logs/`: 로그 파일들(위 규칙으로 이미 이름·내용이 없음).
  - `diag/`: 문서 폴더의 「기기 점검」 결과 파일이 있으면 최근 3개.
  - **넣지 않음**: DB 파일, 사진·음성, 백업 파일, 리포트, 학생 명단.
- 만들기 전에 화면에 무엇이 들어가는지 목록을 보여 주고 「만들기」를 누르게 한다.
- `docs/MANUAL.md`의 「문의할 때」와 `docs/INSTALL.md`를 이 기능으로 갱신.

## 테스트 기준

- 로거: 줄 형식, 5MB 넘으면 돌리기·3개 유지, 경로의 사용자 이름 가리기, 이름이 든 오류를 기록해도 학생 이름이 파일에 없음(학급 명단 대조 필터).
- 진단 파일: 들어가는 파일 목록이 정확히 위와 같음(DB·미디어·백업 없음), `about.json` 필드.
- 패닉 훅이 로그에 남는지(테스트에서 `std::panic::catch_unwind`로).
- 프런트엔드: 오류 경계가 렌더링 오류를 잡아 안내를 보이는지(스모크에서 일부러 오류를 내는 디버그 전용 방법 — 예: `?crash=1`은 디버그 빌드에서만).
